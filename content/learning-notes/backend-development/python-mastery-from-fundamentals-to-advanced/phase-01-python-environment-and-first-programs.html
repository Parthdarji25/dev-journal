#python#phase-01#python-foundations#interpreter#cpython#bytecode#repl#path#indentation#print#input

Phase 01 — Python Environment & First Programs (Part I: Python Foundations). Python is a readable, general-purpose language: when you run a .py file, CPython compiles the whole file to bytecode, then executes it on the Python Virtual Machine.

Key ideas

  • The whole file is compiled before any line runs, so a SyntaxError anywhere stops everything, while a runtime error stops only at the failing line.
  • Bytecode is not machine code. The Python Virtual Machine, a C program inside CPython, executes it.
  • Python is the language; CPython is its reference implementation in C.
  • PATH decides which python runs. Check sys.executable and install with python -m pip.
  • Use Python 3.14 (or 3.15). Micro upgrades are safe; minor upgrades need testing. Never use Python 2.
  • The REPL auto-displays expression values; scripts only show what you print().
  • Indentation defines blocks: a line ending in : plus 4 spaces, never mixed with tabs.
  • Expressions produce values; statements perform actions. = assigns, == compares.
  • print() displays text and returns None. input() always returns a str, so convert and validate it.
  • Start every script with the main() + if __name__ == "__main__": pattern.

1. What Python is

First principles

A CPU only understands machine code: long sequences of numbers meaning things like "add these two values" or "jump to this memory address." Humans are very bad at writing that directly. A programming language is a precise, human-readable way to write instructions, together with a program that translates them into something the machine can run.

Analogy: you write a recipe in English, and a translator turns it into a very simple instruction set for a kitchen robot. Python is the English recipe; the interpreter is the translator and the robot together.

Python is a high-level, general-purpose programming language designed for readability.

Why it exists

  • Guido van Rossum started Python as a hobby project in late 1989; the first public release came in 1991. The name comes from Monty Python, not the snake.
  • Programmers then had two main options: C, which was fast and powerful but slow to write and easy to get wrong, and shell scripts, which were quick to write but messy for anything non-trivial.
  • Python aimed for the middle: as easy as a script, structured enough for real programs, and above all readable.
  • Core belief: code is read far more often than it is written.

How it works

Term Plain meaning
High-level You describe what you want ("sort this list"), not how the hardware does it.
General-purpose Not built for one job: web, data, AI, automation, DevOps, testing and science.
Dynamically typed Types are worked out while the program runs. You don't declare them.
Garbage collected Python frees memory you no longer use.
Interpreted (mostly) You run the source directly; behind the scenes it's compiled to bytecode first (section 2).
Batteries included A large standard library ships with Python (json, math, pathlib, …).

When raw speed matters, Python calls fast code written in C underneath, which is why it's both productive and practical.

Simple example

names = ["Asha", "Ravi", "Meera"]
for name in names:               # reads almost like English
    print(f"Hello, {name}!")     # Hello, Asha!  Hello, Ravi!  Hello, Meera!

Real-world example

Area Real-world examples
Web backends Instagram (Django); FastAPI powers many modern APIs
Data and AI pandas (data analysis), PyTorch and scikit-learn (machine learning), LLM applications
Automation Renaming thousands of files, scraping websites, filling spreadsheets
DevOps and cloud Deployment scripts, infrastructure tooling
Testing Automated test suites, even for code written in other languages
Science Physics simulations, astronomy, bioinformatics

A small automation script, the kind of job Python is famous for:

from pathlib import Path

total = 0.0
for receipt in Path("receipts").glob("*.txt"):   # every .txt file in the receipts folder
    total += float(receipt.read_text())           # each file holds one amount, e.g. "249.50"

✅ Correct code

months_per_year = 12

❌ Incorrect code and why it fails

message = "Hello"
print(mesage)

NameError: name 'mesage' is not defined. Did you mean: 'message'?

Print("Hello")

NameError: name 'Print' is not defined. Did you mean: 'print'?

Why: readable doesn't mean forgiving. Python never guesses what you meant. Names must match exactly, and Python is case-sensitive: print, Print and PRINT are three different names.

2. How Python code executes

First principles

Your CPU understands only machine code: numbers that mean tiny actions like "add these two values" or "jump to this memory address." It cannot read price * 0.18. Something has to translate your text into actions. There are two classic ways to do that:

Strategy How it works Analogy Examples
Compile ahead of time Translate the whole program into machine code first, then run that A translator converts a whole book before anyone reads it C, Rust, Go
Interpret A program reads your code and carries it out as it goes A live interpreter translating a speech sentence by sentence Early BASIC, shell scripts

CPython uses a mix of both:

  1. It first translates your whole file into a simpler language called bytecode. That's the "compile" part.
  2. Then a program inside CPython, the Python Virtual Machine (PVM), reads that bytecode and carries it out, one instruction at a time. That's the "interpret" part.

Analogy: a chef gets a recipe in your handwriting. First they rewrite the whole recipe as a clean, numbered checklist of simple steps (compile), and they refuse to start if any line is unreadable (SyntaxError). Then they cook by following the checklist one step at a time (execute). Something can still go wrong while cooking, like running out of an ingredient (runtime error), but only at that step.

Key words:

Term Plain meaning
Source code The text you write in a .py file
Token One meaningful piece of that text: a name, a number, a symbol, a keyword
AST (Abstract Syntax Tree) A tree that describes the structure of your code: "assign the result of multiplying price by 0.18 to tax"
Bytecode A list of simple instructions for the Python Virtual Machine. Not CPU machine code
PVM (Python Virtual Machine) The loop inside CPython that executes bytecode instructions one by one
Interpreter The whole python program (CPython), which contains all of the stages below

Why it exists

Why not just translate straight to machine code, or re-read the text line by line?

  • Portability: bytecode is the same on every computer. Only the PVM needs to be built for each type of CPU, and CPython's C code already is. Your .py files run anywhere Python is installed, with no separate build per machine.
  • Speed: re-reading and re-understanding text every time a line runs (for example, inside a loop that repeats a million times) would be very slow. Bytecode is understood once and then executed quickly.
  • Simplicity: producing optimized machine code for every CPU is extremely hard. One virtual machine written in C is far simpler to build and maintain.
  • Early error detection: because the whole file is checked before anything runs, grammar mistakes are reported immediately instead of halfway through a job.
  • Caching: bytecode can be saved to disk (.pyc files), so large apps don't redo the translation on every start.

How it works

           your file (text)
                 │
   ┌─────────────▼─────────────┐
   │ 1. TOKENIZE               │  text  →  tokens          ← unclosed strings caught here
   ├───────────────────────────┤
   │ 2. PARSE                  │  tokens →  AST (a tree)   ← grammar errors caught here
   ├───────────────────────────┤
   │ 3. COMPILE                │  AST    →  bytecode
   └─────────────┬─────────────┘
                 │   ↑ steps 1–3 happen for the WHOLE file before anything runs
   ┌─────────────▼─────────────┐
   │ 4. EXECUTE (the PVM)      │  runs bytecode one instruction at a time
   └───────────────────────────┘                            ← runtime errors happen here

We'll follow one small file through every stage:

# bill.py
price = 100
tax = price * 0.18
print(price + tax)

Stage 1: Tokenize — split the text into pieces

Python reads the text character by character and groups it into tokens, the way you'd split a sentence into words and punctuation. Line 2 becomes:

NAME 'tax'   OP '='   NAME 'price'   OP '*'   NUMBER '0.18'   NEWLINE
  • Spaces between tokens and comments are thrown away here. That's why comments never affect your program.
  • Indentation is turned into special INDENT/DEDENT tokens, which is how Python knows where blocks start and end.
  • Errors caught here: text that can't even be split into valid pieces, such as print("hi) → SyntaxError: unterminated string literal.

Stage 2: Parse — check the grammar and build a tree

The parser checks the tokens against Python's grammar rules ("an assignment is a target, then =, then an expression"). If they fit, it builds an AST. Line 2 becomes this tree:

Assign
├── target: Name 'tax'                 (store into tax)
└── value:  BinOp  (multiply)
            ├── left:  Name 'price'    (read price)
            └── right: Constant 0.18
  • The tree captures meaning and order: "multiply first, then assign."
  • Errors caught here: valid tokens in an invalid order, such as a missing : after if, an unclosed (, or if x = 5:. All of these are SyntaxError (or its subclass IndentationError).

Stage 3: Compile — turn the tree into bytecode

The compiler walks the tree and writes a list of simple instructions. Line 2 becomes:

LOAD_NAME    price     # look up the value of "price"
LOAD_CONST   0.18      # get the constant 0.18
BINARY_OP    *         # multiply the two values
STORE_NAME   tax       # save the result under the name "tax"
  • The compiler also does small optimizations. For example, x = 2 + 3 is compiled as if you had written x = 5.
  • For imported modules, the bytecode is cached as a .pyc file in a __pycache__/ folder, so the next import can skip stages 1–3. (The main script you run directly isn't cached.)

Stage 4: Execute — the Python Virtual Machine runs the bytecode

The PVM is a loop written in C: fetch the next instruction → do it → move on, until the end. It works with a stack, a pile of values where you can only add to the top or take from the top, like a stack of plates.

Here is the PVM running line 2, assuming line 1 already stored price = 100:

Instruction What the PVM does Stack afterwards
LOAD_NAME price Looks up price, pushes its value [100]
LOAD_CONST 0.18 Pushes the constant [100, 0.18]
BINARY_OP * Pops two values, multiplies them, pushes the result [18.0]
STORE_NAME tax Pops the top value and saves it as tax []

Line 3 works the same way: it loads print, price and tax, adds price + tax to get 118.0, then calls print with it. Output:

118.0
  • Runtime errors happen during this stage, at the exact instruction that fails: LOAD_NAME can't find a name → NameError; BINARY_OP divides by zero → ZeroDivisionError.
  • When an error isn't handled, the PVM stops and prints a traceback. Read its last line first (the error type and message), then read upward to find the file and line number.

Where each kind of error comes from

Stage Example code Error Does earlier code run?
1. Tokenize print("hi) SyntaxError: unterminated string literal No, nothing runs
2. Parse if total > 5 SyntaxError: expected ':' No, nothing runs
2. Parse badly indented line IndentationError: unexpected indent No, nothing runs
4. Execute print(totl) NameError: name 'totl' is not defined Yes, until this line
4. Execute print(10 / 0) ZeroDivisionError: division by zero Yes, until this line

The one rule to remember: stages 1–3 process the whole file before stage 4 starts. So a SyntaxError anywhere stops everything, while a runtime error stops only at the line where it happens.

Simple example

You can watch every stage yourself on bill.py:

python -m tokenize bill.py   # stage 1: shows every token
python -m ast bill.py        # stage 2: shows the AST
python -m dis bill.py        # stage 3: shows the bytecode
python bill.py               # all 4 stages: prints 118.0

Or inside Python:

import dis                   # "dis" = disassembler: shows the bytecode Python generated
dis.dis("tax = price * 0.18")

LOAD_NAME    price
LOAD_CONST   0.18
BINARY_OP    5 (*)
STORE_NAME   tax
...                          # exact instructions vary between Python versions

Real-world example

  • A web service has a typo in one rarely used module. Because every imported module goes through stages 1–3 when it's loaded, the server fails to start at all, even though the broken code would almost never run. That's why teams check syntax and run linters in CI before deploying.
  • A Django or FastAPI app imports hundreds of modules at startup. Cached .pyc files mean those modules don't go through stages 1–3 again on every restart.

✅ Correct code

python -m py_compile app.py   # runs stages 1–3 only: reports any SyntaxError without running the program

A file with valid grammar passes stages 1–3, then runs top to bottom:

print("Line 1 runs")
print("Line 2 runs")
print("Line 3 runs")

❌ Incorrect code and why it fails

A runtime error (valid grammar, fails in stage 4):

print("Line 1 runs")
print("Line 2 runs")
print(10 / 0)          # crashes HERE
print("Line 4 runs")   # never reached

Line 1 runs
Line 2 runs
Traceback (most recent call last):
  File "file_a.py", line 3, in <module>
    print(10 / 0)
ZeroDivisionError: division by zero

A syntax error (invalid grammar, fails in stage 2):

print("Line 1 runs")
print("Line 2 runs")
print("Line 3"         # missing closing parenthesis
print("Line 4 runs")

  File "file_b.py", line 3
    print("Line 3"
         ^
SyntaxError: '(' was never closed

Why: in the second file nothing prints, not even line 1. The parser rejects the whole file in stage 2, so stage 4 never starts. In the first file, stages 1–3 succeed, so lines 1 and 2 actually run before stage 4 hits the division by zero.

E2. Explain the difference between bytecode and machine code in 2–3 sentences.

Answer: machine code is the instruction set the CPU runs directly, and it's specific to the hardware. Bytecode is a simpler, portable instruction set that Python generates from your source code. The CPU can't run it; the Python Virtual Machine reads each instruction and carries it out.

E3. Run dis.dis("x = 2 + 3"). What do you notice?

Answer: the bytecode loads the constant 5 directly and stores it in x. There's no addition instruction: the compiler worked out 2 + 3 ahead of time (this is called constant folding). It shows that compilation really happens before execution.

3. What happens when you run a .py file

First principles

A .py file is just text sitting on your disk. It can't do anything by itself. "Running" it means starting a program, the Python interpreter, and handing it the path of that text file.

Why it exists

Knowing the exact sequence of steps tells you where any problem comes from:

  • 'python' is not recognized → the shell couldn't find the interpreter (step 1).
  • SyntaxError → compilation failed (step 4).
  • ZeroDivisionError, NameError and friends → execution failed (step 6).
  • A non-zero exit code → the program reported failure to the operating system (step 7).

How it works

python hello.py:

  1. The shell finds the python program by searching the folders in PATH.
  2. The interpreter starts up: it prepares the built-ins (print, len, …), the module search path and memory management.
  3. It reads hello.py as text (UTF-8).
  4. It compiles the entire file to bytecode. A syntax error stops everything here.
  5. It sets the special variable __name__ to "__main__", marking this file as the program being run directly.
  6. It executes the bytecode from top to bottom.
  7. It exits with an exit code: 0 means success; anything else (such as 1 after an unhandled exception) means failure.

What the interpreter does overall: starts up, reads, compiles, executes, manages memory, reports errors as tracebacks, and returns an exit code.

Simple example

# hello.py
print("Starting...")
name = "Asha"
print("Hello,", name)

$ python hello.py
Starting...
Hello, Asha

Real-world example

A nightly backup script is started by a scheduler. Nobody watches it, so the scheduler uses the exit code to decide whether to send an alert:

python backup.py && echo "Backup OK" || echo "Backup FAILED"   # && runs only when the exit code is 0

CI pipelines (Phase 71) work the same way: a step fails if its command exits with a non-zero code.

✅ Correct code

"""check_run.py: Shows how the file was started."""
import sys

print(__name__)       # __main__ when run directly with: python check_run.py
sys.exit(0)           # explicit success exit code (the default at the end of a script anyway)

❌ Incorrect code and why it fails

greet()              # NameError: name 'greet' is not defined

def greet():
    print("Hi")

Why: the whole file is compiled first, but it's executed top to bottom. def is a statement that creates the function only when that line runs. On line 1 the function doesn't exist yet. Fix: define the function before calling it, or put the call inside main() as shown in section 9.

Exercises

E1. Put these steps in the right order: execute bytecode · compile to bytecode · shell finds python via PATH · exit with a code · interpreter starts up · read the file · set __name__ to "__main__".

Answer: shell finds python via PATH → interpreter starts up → read the file → compile to bytecode → set __name__ to "__main__" → execute bytecode → exit with a code.

E2. At which step does each problem happen? (a) 'python' is not recognized, (b) SyntaxError: expected ':', (c) ZeroDivisionError: division by zero.

Answer: (a) step 1, finding the program; (b) step 4, compiling; (c) step 6, executing.

E3. A script ends with an unhandled ValueError. What exit code does it return, and who cares?

Answer: 1. Schedulers, shell scripts and CI pipelines read it to know the program failed.

Debugging problems

D1. A beginner writes this and says: "Python is broken. My first print didn't even run, but the bug is on line 4!"

print("Program started")
total = 5 + 3
print("Total is", total)
if total > 5
    print("Big number")

Answer:

  1. Error: SyntaxError: expected ':' on line 4.
  2. "Program started" doesn't print because Python compiles the whole file before executing anything. Invalid grammar anywhere stops the entire file at step 4, so step 6 never starts.
  3. Fix: if total > 5:. The output is then Program started, Total is 8, Big number.

4. Installing Python and PATH

First principles

Your computer can't run .py text on its own. It needs the interpreter program on disk. Installing Python puts three things on your machine:

  1. The interpreter (python)
  2. The standard library (math, json, pathlib, datetime, …), Python's "batteries included"
  3. pip, the tool for installing third-party packages such as FastAPI

When you then type python, your shell has to find that program. It doesn't search your whole disk. It checks a short list of folders stored in an environment variable called PATH, in order, and runs the first match.

Why it exists

  • Without an installed interpreter, there's nothing to run your code.
  • PATH lets you type python instead of a full path like C:\Users\you\AppData\Local\Programs\Python\Python314\python.exe every time.

How it works

OS How to install
Windows python.org, using the Python install manager (py install 3.14). The py launcher runs installed versions. With a traditional installer, tick "Add python.exe to PATH".
macOS The python.org installer, or brew install python@3.14. Don't modify the Python that macOS itself relies on.
Linux Usually preinstalled as python3. Install extras with your package manager. Never remove the system Python: the OS depends on it.
Any OS uv python install 3.14, a modern version manager (covered in Phase 16)

PATH rules:

  • Python's folder isn't in PATH → 'python' is not recognized…
  • Two Pythons are in PATH → the first match wins, which may not be the one you expect.
  • A terminal reads PATH when it opens, so changes only apply to newly opened terminals.
PATH = C:\Windows\System32 ; C:\Users\you\AppData\Local\Programs\Python\Python314 ; ...
         └ checked 1st ┘        └ checked 2nd ┘

Simple example

python --version      # Windows (or: py --version)
python3 --version     # macOS / Linux

Python 3.14.0

Real-world example

Your team's README says "requires Python 3.14". Before you start, you prove which interpreter you're actually using, and you install packages through that exact interpreter:

import sys
print(sys.executable)   # e.g. /usr/local/bin/python3.14: the exact interpreter running this code
print(sys.version)      # its exact version

which python3                     # macOS/Linux: which file the command resolves to
where python                      # Windows: every match, in PATH order
python -m pip install fastapi     # installs into the SAME Python you will run

✅ Correct code

python -m pip install requests   # runs pip *through* this python: no mismatch possible
python app.py

❌ Incorrect code and why it fails

pip install requests     # succeeds...
python app.py

ModuleNotFoundError: No module named 'requests'

Why: with two Pythons installed, bare pip can belong to a different installation from python. The package went into one interpreter and the script ran on the other. Each installation has its own separate set of packages.

Exercises

E1. Verify your setup and write down the results.

python --version          # or python3 / py

import sys, platform
print(sys.executable)
print(platform.python_implementation())
print(platform.python_version())

Answer: results vary by machine. Check that the version is 3.10 or newer (ideally 3.14 or 3.15), that the implementation is CPython, and that sys.executable points to the Python you installed, not an older copy you'd forgotten about.

E2. where python on Windows prints two paths. Which one runs when you type python?

Answer: the first one listed. PATH is searched in order and the first match wins.

Debugging problems

D1. A student installs Python on Windows, opens a terminal, types python --version and gets 'python' is not recognized as an internal or external command. Give two likely causes and fixes.

Answer:

  • Python's folder isn't in PATH (the "Add to PATH" box wasn't ticked). Re-run the installer, choose Modify and add it to PATH, add the folder manually in Environment Variables, or use the py launcher, which doesn't depend on PATH.
  • The terminal was opened before Python was installed, so it never saw the new PATH. Close it and open a new one.
  • Also possible: typing python opens the Microsoft Store because of a Windows "app execution alias". Turn it off under Settings → Apps → Advanced app settings → App execution aliases, or use py.

D2. A developer runs pip install requests (success), then python app.py gives ModuleNotFoundError: No module named 'requests'. They have two Pythons installed. What happened, and how do you prove it?

Answer: pip and python belong to different installations: the package went into Python A, but the script ran on Python B. Proof: compare the path shown by pip --version with print(sys.executable) inside app.py; they won't match. Fix: python -m pip install requests, and later use one virtual environment per project (Phase 16).

5. Python versions

First principles

A language keeps changing: new features arrive, old ones are removed, bugs get fixed. A version number communicates how big a change is, so you know whether upgrading is safe and which features you can use.

3 . 15 . 0
major . minor . micro

Why it exists

  • It tells you at a glance whether an upgrade can break your code.
  • It tells you which syntax and features are available. Code written for 3.10 may not run on 3.9.
  • Python 2 → 3 is the reason to take this seriously. Python 3 (2008) fixed deep design problems, but that meant breaking backward compatibility: Python 2 code often doesn't run on Python 3. Python 2 reached end of life on January 1, 2020.

How it works

Part Meaning Is upgrading safe?
major Huge, breaking changes (only ever happened once, 2 → 3) —
minor New features, released every October; may remove deprecated features Test first
micro Bug and security fixes only Yes, apply promptly
  • Each minor version gets about 2 years of bug fixes, then security fixes only, and reaches end of life after about 5 years.
  • As of October 2026: Python 3.15 is the newest release (one notable change: UTF-8 is now the default encoding). Python 3.14 is the safest choice for this roadmap because every library supports it. Avoid anything below 3.10.

Simple example

import sys
print(sys.version_info)              # sys.version_info(major=3, minor=14, micro=0, ...)
print(sys.version_info >= (3, 10))   # True when running Python 3.10 or newer

Real-world example

A project states the versions it supports in its pyproject.toml (Phase 16), and its CI runs the tests on several versions before the team upgrades:

[project]
name = "expense-tracker"
requires-python = ">=3.12"   # pip refuses to install it on older Pythons

Professional habit: choose a version all your dependencies support, pin it, and upgrade deliberately once the tests pass, not on release day.

✅ Correct code

import sys

if sys.version_info < (3, 10):                                 # compares numbers part by part
    sys.exit("This program needs Python 3.10 or newer.")       # prints the message, exits with code 1
print("Version OK")

❌ Incorrect code and why it fails

print "Hello"

SyntaxError: Missing parentheses in call to 'print'. Did you mean print(...)?

Why: this is Python 2 syntax. In Python 3, print is a function, and calling a function needs parentheses. If a tutorial writes this, it's outdated.

print("3.9" < "3.10")   # False!

Why: strings are compared character by character, and "9" comes after "1". Version strings must never be compared as text. Use sys.version_info with tuples like (3, 10).

Exercises

E1. For 3.13.7, name the major, minor and micro parts. Is upgrading 3.13.7 → 3.13.8 safe? What about 3.13 → 3.14 for a large project?

Answer: major 3, minor 13, micro 7.

  • 3.13.7 → 3.13.8 is safe: micro releases contain only bug and security fixes.
  • 3.13 → 3.14 is not automatically safe: minor releases add features and can remove deprecated ones, and dependencies may lag. A professional team checks dependency support, runs the full test suite on 3.14 (usually in CI), fixes warnings, then switches.

E2. Which version would you choose? (a) a new learning project today, (b) a project whose main library only supports up to 3.13.

Answer: (a) 3.14 (3.15 also works for learning). (b) 3.13: the dependency decides, until it adds support for newer versions.

Debugging problems

D1. This code works on a teammate's laptop, but fails on yours with SyntaxError: invalid syntax on the match line. python --version shows Python 3.9.18. Why?

command = "start"
match command:
    case "start":
        print("Starting")

Answer: the match statement was added in Python 3.10. Python 3.9 doesn't know this syntax, so it fails during parsing. Fix: install Python 3.10+ (ideally 3.14). Rewriting it with if/elif would work too, but upgrading is the right fix, because 3.9 has reached end of life.

6. CPython and other implementations

First principles

"Python" means two separate things:

  1. Python the language: the specification, the rules of what valid code is and what it should do.
  2. A Python implementation: an actual program that runs Python code.

CPython is the official, reference implementation, written in C. When you download Python from python.org, you get CPython. When people say "Python," they almost always mean CPython.

Why it exists

One language can have several implementations, each built for a different goal:

Implementation What it is Why it exists
CPython The reference implementation, in C The standard: widest library support
PyPy Python with a JIT compiler Much faster for long-running, pure-Python code
MicroPython A tiny Python Runs on microcontrollers (ESP32, Raspberry Pi Pico)
GraalPy Python on GraalVM Works alongside Java
Jython / IronPython Python on the JVM / .NET Mostly historical today

How it works

  • CPython follows exactly the pipeline in section 2: tokenizer, parser, compiler, bytecode and a virtual machine loop written in C.
  • Many popular libraries (NumPy, database drivers) contain C code written against CPython's C API. That's a big reason CPython has the widest library support.
  • Some behavior, such as reference counting and the GIL (Phases 26, 29 and 42), is a CPython detail, not a language guarantee. Interviewers like to check whether you know that.

Simple example

import platform
print(platform.python_implementation())   # 'CPython'
print(platform.python_version())          # e.g. '3.14.0'

Real-world example

  • A FastAPI backend deployed with the official python:3.14 Docker image runs on CPython.
  • A home weather station reads a temperature sensor on a $5 ESP32 board running MicroPython.

✅ Correct code

import platform

if platform.python_implementation() != "CPython":
    print("Warning: this tool is only tested on CPython")   # be explicit about what you support

❌ Incorrect code and why it fails

A desktop script copied onto an ESP32 board running MicroPython:

import requests     # ImportError: no module named 'requests'

Why: MicroPython is a separate, much smaller implementation. It ships only a small subset of the standard library and can't install normal PyPI packages with pip. Same language, different implementation, different available modules.

Exercises

E1. Which implementation fits each case? (a) a normal FastAPI backend, (b) code on a $5 microcontroller, (c) a long-running, pure-Python number-crunching script where speed matters.

Answer: (a) CPython: the standard, and every library supports it. (b) MicroPython: small enough for devices with very little memory. (c) PyPy is a good candidate, because its JIT speeds up pure-Python loops a lot. Measure first, though: with C-heavy libraries like NumPy, CPython is often as fast or faster.

E2. True or false: "Code that works on CPython behaves identically on every implementation."

Answer: false. All implementations follow the same language rules, but implementation details differ: speed, memory behavior, which C-based libraries work, and how much of the standard library is available.

Debugging problems

D1. You and a teammate run the same pure-Python benchmark. Theirs is five times faster. Your check script prints CPython 3.14.0; theirs prints PyPy 7.3.x. Explain the difference.

Answer: they're running a different implementation. PyPy's JIT compiler turns hot pure-Python loops into machine code while the program runs, which can be much faster than CPython's bytecode loop for this kind of code. It's not a bug. Always compare benchmarks on the same implementation and version.

7. The REPL

First principles

REPL stands for Read → Eval → Print → Loop:

  1. Read: it reads one line, or one block, of code that you type.
  2. Eval: it compiles and executes that code.
  3. Print: if the code produced a value, it shows it.
  4. Loop: it goes back to step 1.

Why it exists

Sometimes you want an answer right now: Does this method exist? What does this expression return? Creating a file just to check one line would be slow. The REPL gives instant feedback.

How it works

python        # Windows (or: py)
python3       # macOS / Linux
Prompt Meaning
>>> Ready for a new statement
... Continuing a block; press Enter on an empty line to finish it
  • The REPL automatically displays the value of expressions. Scripts do not.
  • It doesn't display None, so calls like print("hi") show only their output.
  • _ holds the last value it displayed.
  • Since Python 3.13 the REPL has colors and multi-line editing, and exit works without parentheses.
  • Leave with exit(), or Ctrl+D (macOS/Linux) / Ctrl+Z then Enter (Windows).

Simple example

>>> 2 + 3              # expression: shown automatically
5
>>> name = "Asha"      # assignment: produces no value, so nothing is shown
>>> name
'Asha'
>>> if name:           # block: the prompt changes to "..."
...     print("Hi")
...
Hi
>>> _                  # last displayed value
'Asha'

Real-world example

Before putting a date format into an API response, you check it in seconds:

>>> from datetime import date
>>> date(2026, 10, 15).strftime("%d %b %Y")
'15 Oct 2026'
>>> dir("hello")[-5:]        # explore what methods an object has
['swapcase', 'title', 'translate', 'upper', 'zfill']
>>> help(str.title)          # read the documentation (press q to quit)

python -i script.py runs a script and then opens the REPL with all its variables, which is handy for inspecting state after a crash.

✅ Correct code

>>> "backend developer".title()
'Backend Developer'
>>> exit()

$ python --version      # shell commands go in the terminal, AFTER leaving the REPL
Python 3.14.0

❌ Incorrect code and why it fails

>>> python --version
  File "<stdin>", line 1
    python --version
           ^^^^^^^^^
SyntaxError: invalid syntax

Why: python --version is a shell command. Once you're inside Python (the >>> prompt), everything you type is treated as Python code, and this isn't valid Python. Exit first, then run it in the terminal.

Exercises

E1. In the REPL, type 10 * 4. Then put 10 * 4 on its own line in a file and run the file. Why is the result different?

Answer: the REPL shows 40; the script shows nothing. The REPL auto-displays expression values, while a script computes 40 and throws it away unless you print() it.

E2. Predict exactly what the REPL shows for each line, in order: x = 5, x, x * 2, _, print("hi").

Answer: nothing; 5; 10; 10; hi. The last call returns None, which the REPL doesn't display.

Debugging problems

D1. A student copies a REPL session into calc.py and runs it:

>>> total = 5 + 3
>>> total

They get SyntaxError: invalid syntax. Why? And after removing the >>> prompts, why does nothing print?

Answer: >>> is the REPL's prompt, not Python code, so the file isn't valid Python. After removing the prompts, the file runs, but total on its own line is just an expression: scripts don't auto-display values. Use print(total).

8. .py files

First principles

A .py file is a plain-text file containing Python code, saved in UTF-8. The .py extension tells editors and the operating system "this is Python," but the content is just text. When one file imports another, the file name (without .py) becomes the module name.

Why it exists

Anything typed in the REPL disappears when you exit. A file is saved, reusable, shareable and version-controlled with Git, and other files can import it. All real programs live in files.

How it works

  • Because a file name becomes a module name, it must be a valid Python name: letters, digits and underscores, not starting with a digit.
  • When you run a script, Python searches the script's own folder first for imports. A file of yours with the same name as a standard-library module will be imported instead of the real one. This is called shadowing.
✅ Good name ❌ Bad name Problem
invoice_report.py Invoice Report.py Spaces break imports and terminal commands
user_utils.py user-utils.py Hyphens can't be used in import
dice_roller.py random.py, json.py, math.py, email.py Shadows a standard-library module
main.py 1st_program.py A module name can't start with a digit

Rule: use lowercase_with_underscores.py, as PEP 8 recommends.

Simple example

# greet.py
print("Hello from a file!")

python greet.py      # Hello from a file!

Real-world example

A small project split into files, each with one job:

expense_tracker/
├── main.py        # starts the program
├── storage.py     # reads and saves expenses
└── report.py      # builds the monthly summary

# main.py
import report      # finds report.py in the same folder; module name = file name

report.print_summary()

✅ Correct code

# report.py  (valid module name)
def print_summary() -> None:
    print("Monthly summary: ₹12,450 spent")

# main.py
import report
report.print_summary()   # Monthly summary: ₹12,450 spent

❌ Incorrect code and why it fails

The same helper saved as user-utils.py:

import user-utils

SyntaxError: invalid syntax

Why: Python reads user-utils as user minus utils, an expression, not a module name. Module names follow the same rules as variable names, so the file must be called user_utils.py.

Exercises

E1. Which file names are fine, and what's wrong with the others? Monthly Report.py, monthly_report.py, 2nd_try.py, email.py, price-check.py, price_check.py.

Answer:

  • Fine: monthly_report.py, price_check.py.
  • Monthly Report.py: has a space (and capitals, against PEP 8).
  • 2nd_try.py: starts with a digit.
  • email.py: shadows the standard-library email module.
  • price-check.py: the hyphen can't be imported.

E2. Why should code live in .py files rather than only in the REPL?

Answer: REPL code disappears when you exit. Files are saved, can be re-run, shared, imported by other files and tracked with Git.

Debugging problems

D1. A student creates a file named random.py containing:

import random

print(random.randint(1, 6))

They get:

AttributeError: partially initialized module 'random' has no attribute 'randint'
(most likely due to a circular import)

Newer Python versions add a hint like "consider renaming 'random.py'…". Why does this happen?

Answer: when Python handles import random, it searches the script's own folder first. It finds the student's random.py and imports that file instead of the standard library's random. That file is only half-loaded at that moment and has no randint. Fix: rename it, for example to dice_roller.py, and delete any leftover __pycache__ folder. Never name files after standard-library modules.

9. Running code from the terminal

First principles

A terminal (shell) is a text interface to your operating system: you type a command, it runs a program. At any moment the terminal is "inside" one folder, the current working directory. Relative file names like hello.py are looked up in that folder.

Why it exists

Servers, schedulers, Docker containers and CI pipelines have no "Run" button. They start Python with a command. Running from the terminal is how Python runs in the real world, so a professional must be comfortable with it.

How it works

cd path/to/my_project    # change directory
ls                       # macOS/Linux: list files (Windows: dir)
python hello.py          # run the file in the CURRENT folder
Command What it does When to use it
python file.py Runs a script Most of the time
python -i file.py Runs the script, then opens the REPL with its variables Inspecting state after a run
python -c "print(2**10)" Runs code given as text (no auto-display of values) Shell one-liners
python -m module Runs a module found by its name python -m pip, python -m venv

Exit codes:

python hello.py
echo $?              # macOS/Linux       → 0 means success
echo $LASTEXITCODE   # Windows PowerShell

Professional script structure (fully explained in Phase 15):

"""greet.py: Greets the user."""     # module docstring: what this file is for

def main() -> None:                    # all the program's logic lives in a function
    print("Hello from main!")

if __name__ == "__main__":             # True only when this file is run directly
    main()                             # importing this file will NOT run main()

Simple example

cd projects
python hello.py

Hello, world!

Real-world example

A daily report runs at 07:00 on a Linux server, started by cron with no human present:

# crontab entry: minute hour day month weekday  command
0 7 * * * cd /home/asha/reports && /usr/bin/python3 daily_report.py

The command moves into the right folder first, then calls Python with a full path, because a scheduler can't rely on your terminal's PATH or current folder.

✅ Correct code

python -c "print('ready')"            # code in quotes: the shell passes it to Python untouched
python projects/hello.py              # or give the path relative to where you are

❌ Incorrect code and why it fails

python -c print("hi")

bash: syntax error near unexpected token `('

Why: the shell reads the command line before Python ever sees it, and ( has a special meaning to the shell. Wrap the code in quotes: python -c 'print("hi")'.

python hello.py     # while in the wrong folder

python: can't open file '/Users/you/hello.py': [Errno 2] No such file or directory

Why: Python looks for hello.py in the current folder only.

Exercises

E1. Create about_me.py that prints your name, your city and your goal on three lines. Use the main() structure. Run it from the terminal, then check its exit code.

Answer:

"""about_me.py: Prints a short introduction."""

def main() -> None:
    print("Name: Riya")
    print("City: Mumbai")
    print("Goal: Become a professional Python backend developer")

if __name__ == "__main__":
    main()

python about_me.py
echo $?             # or $LASTEXITCODE on PowerShell → 0

E2. Predict what each command prints.

python -c "print(3 * 'ab')"
python -c "2 + 2"

Answer: the first prints ababab (multiplying a string by an integer repeats it). The second prints nothing: code run with -c behaves like a script, not like the REPL.

Debugging problems

D1. A student's terminal is in C:\Users\riya. Their file is at C:\Users\riya\projects\hello.py. They run python hello.py and get [Errno 2] No such file or directory. What's wrong, and what are two ways to fix it?

Answer: Python looks for C:\Users\riya\hello.py, which doesn't exist: the file is in the projects subfolder. Fixes: cd projects then python hello.py, or run python projects\hello.py.

10. Indentation

First principles

Code has structure: these lines belong to the if, and those lines run afterward. Every language needs a way to mark where a block starts and ends. Languages like C and JavaScript use curly braces { } and treat indentation as decoration. Python uses the indentation itself: the indentation is the structure.

Why it exists

Readability. In brace-based languages, indentation can lie: code can look nested when it isn't. In Python, what you see is what runs, and every Python codebase looks consistent.

How it works

  1. A line that opens a block ends with a colon (:): if, else, for, while, def, class and others.
  2. The lines inside the block are indented further than the line that opened it.
  3. The block ends when the indentation returns to the previous level.
  • Use 4 spaces per level (PEP 8). Set your editor so the Tab key inserts 4 spaces (VS Code does this for Python by default).
  • Never mix tabs and spaces. A tab can look like 4 or 8 spaces depending on the editor, so Python 3 raises a TabError instead of guessing.

Simple example

temperature = 38

if temperature > 37:                   # colon: a block starts here
    print("You have a fever.")         # inside the if (4 spaces)
    print("Please rest.")              # still inside the if
print("Check complete.")               # back at the outer level: always runs

Real-world example

An online shop decides the delivery charge:

cart_total = 1200

if cart_total >= 999:
    shipping = 0
    print("Free delivery applied")
else:
    shipping = 49
print(f"Shipping: ₹{shipping}")        # outside both blocks: runs for every order

✅ Correct code

age = 20
if age >= 18:
    print("Adult")
    print("Can vote")
print("Done")

❌ Incorrect code and why it fails

if temperature > 37:
print("Fever")

IndentationError: expected an indented block after 'if' statement on line 1

After a colon, Python expects at least one indented line.

print("Start")
    print("Oops")

IndentationError: unexpected indent

You can't indent unless a block has just been opened.

if temperature > 37:
    print("Fever")
  print("Rest")        # 2 spaces: matches no existing level

IndentationError: unindent does not match any outer indentation level

The dangerous one, a silent logic bug:

if temperature > 37:
    print("You have a fever.")
print("Please rest.")      # meant to be inside the if, but runs for EVERYONE

This runs with no error, but behaves wrongly. Python can't read your intentions, only your indentation.

Exercises

E1. Predict the output with score = 45, then with score = 80.

if score >= 50:
    print("Passed")
    print("Well done")
print("Result recorded")

Answer: with 45: only Result recorded. With 80: Passed, Well done, Result recorded.

Debugging problems

D1. Find every error.

age = 20
if age >= 18
print("Adult")
  print("Can vote")

Answer: three errors: the missing colon on line 2, line 3 not indented, and line 4 indented with 2 spaces, which matches no level. Python reports only the first error it finds, because parsing stops there. Fixed:

age = 20
if age >= 18:
    print("Adult")
    print("Can vote")

D2. This runs with no errors, but a user with a balance of 500 still sees "Purchase approved." Why?

balance = 500
price = 800

if balance < price:
    print("Insufficient funds.")
print("Purchase approved.")

Answer: print("Purchase approved.") isn't indented, so it's outside the if and runs every time. It should run only when funds are sufficient:

if balance < price:
    print("Insufficient funds.")
else:
    print("Purchase approved.")

11. Comments and docstrings

First principles

Everything from a # to the end of that line is a comment: Python ignores it. Comments are for humans. A docstring is different: a real string placed as the first statement of a module, function or class, which Python keeps.

Why it exists

Code shows what happens. Comments explain why: the reasoning, business rules, constraints and anything that isn't obvious. Docstrings document how to use a module, function or class, and tools like help() and editors display them.

How it works

  • Comments are thrown away by the tokenizer (step 1 in section 2). They never reach the bytecode.
  • A # inside a string is just a character, not a comment.
  • Docstrings are string literals stored in the object's __doc__ attribute.
  • PEP 8 style: inline comments have two spaces before # and one space after it.

Simple example

# Full-line comment
tax_rate = 0.18  # inline comment

def area(width: float, height: float) -> float:
    """Return the area of a rectangle."""   # docstring: kept by Python
    return width * height

help(area)       # shows: Return the area of a rectangle.

Real-world example

Comments that record a business rule a newcomer couldn't guess from the code:

# GST on restaurant bills is 5% (no input-tax credit), not the standard 18%.
GST_RATE_RESTAURANT = 0.05

# The payment gateway times out after 30 s, so we give up at 25 s to show our own error.
PAYMENT_TIMEOUT_SECONDS = 25

✅ Correct code

count = count + 1  # the API returns page numbers starting at 0; our users expect 1-based pages

❌ Incorrect code and why it fails

count = count + 1  # add 1 to count

Useless: it repeats the code and adds nothing.

"""
This is not really a comment.
It's an unused string expression.
"""

Works, but it's a misuse. For multi-line comments, start each line with #.

# Apply 10% discount
discount = 0.15

A comment that no longer matches the code. A wrong comment is worse than no comment, because readers trust it. Also avoid leaving old code commented out "just in case": delete it, since Git keeps the history.

Exercises

E1. Rewrite this with good comments. Remove the useless ones and add one that explains why.

# set x to 1440
x = 1440  # x is 1440
# print x
print(x)

Answer: a meaningful name removes the need for most comments:

MINUTES_PER_DAY = 1440  # 24 hours × 60 minutes; used for daily rate-limit resets
print(MINUTES_PER_DAY)

E2. What does this print?

print("Ticket #42")  # print the ticket

Answer: Ticket #42. The # inside the quotes is part of the string. Only the # outside the string starts a comment.

Debugging problems

D1. Customers say they're being given 15% off, but the business rule is 10%. A developer looked at this code and said "it's fine, it applies 10%":

# Apply the 10% loyalty discount
discount = 0.15
final_price = price * (1 - discount)

What went wrong, and what's the fix?

Answer: the developer trusted the comment instead of the code. The code applies 0.15. Fix the value to 0.10 (after confirming the rule) and make sure the comment and code agree. Better still, use a named constant like LOYALTY_DISCOUNT = 0.10, so the code documents itself.

12. Statements vs expressions

First principles

  • An expression is something that produces a value: 5, 5 + 3, len("hello"), price > 100. Test: can it go on the right side of =?
  • A statement is an instruction that does something: x = 5, import math, if x > 3: ..., def f(): ....

Why it exists

Separating the two keeps code clear and catches mistakes. Because assignment is a statement, Python can refuse if x = 5:, a typo that silently causes bugs in languages like C, where assignment is an expression.

How it works

  • Statements often contain expressions: in total = price * qty, the whole line is a statement, and price * qty is an expression inside it.
  • An expression on its own line is also a valid statement, an expression statement: print("hi") is a function-call expression used as a statement.
  • Places that need a value (an if condition, the right side of =, function arguments) accept only expressions.
  • Long expressions can be wrapped in parentheses, and Python joins the lines automatically. Backslash (\) continuation is fragile (a trailing space after it breaks the line), and several statements on one line with ; is bad style.

Simple example

x = 5 + 3        # statement (assignment) containing the expression 5 + 3
x * 2            # expression statement: computes 16, then discards it
print(x > 6)     # True: x > 6 is an expression passed to print

Real-world example

Pricing an order, with a long expression wrapped in parentheses:

price = 499.0
quantity = 3
discount = 100.0
gst_rate = 0.18

total = (                              # one assignment statement...
    (price * quantity - discount)      # ...whose value is one big expression
    * (1 + gst_rate)
)
print(f"Total: ₹{total:.2f}")          # Total: ₹1648.46

✅ Correct code

stock = 0
if stock == 0:                         # == compares and produces True/False
    print("Out of stock")

❌ Incorrect code and why it fails

if x = 5:
    print("five")

SyntaxError: invalid syntax. Maybe you meant '==' or ':=' instead of '='?

Why: an if needs an expression to test, and x = 5 is an assignment statement. Use == to compare. (:=, the "walrus" operator, is an advanced feature covered later.)

result = (y = 10)

SyntaxError: invalid syntax. Maybe you meant '==' or ':=' instead of '='?

Why: assignment isn't an expression, so it produces no value to assign.

Exercises

E1. Label each line as an expression or a statement.

1) 42
2) x = 42
3) x * 2
4) print(x)
5) import os
6) x > 10
7) def hello(): pass

Answer:

Line Type Note
1) 42 Expression
2) x = 42 Statement assignment
3) x * 2 Expression
4) print(x) Expression used as a statement a call produces a value (None)
5) import os Statement
6) x > 10 Expression produces True or False
7) def hello(): pass Statement function definition

E2. In final_price = (price - discount) * 1.18, list every expression.

Answer: price, discount, price - discount, 1.18 and (price - discount) * 1.18. The whole line is an assignment statement.

Debugging problems

D1. Why does this fail, and how do you fix it?

stock = 0
if stock = 0:
    print("Out of stock")

Answer: SyntaxError: invalid syntax. Maybe you meant '==' or ':=' instead of '='?. = assigns; it can't be used as a condition. Fix: if stock == 0:.

13. print()

First principles

Your program runs inside the computer. Without output, you'd have no idea what it computed. print() writes text to standard output (stdout), which is normally your terminal window.

Why it exists

It's the simplest way to show results, messages and progress to a person, and to check values while you're learning.

How it works

print(*objects, sep=" ", end="\n", file=sys.stdout, flush=False)
  1. It converts each object to text with str().
  2. It joins them with sep (a space by default).
  3. It adds end at the very end (a newline by default).
  4. It writes the result to file (the terminal by default).
  5. It returns None.

f-strings are the professional way to build output: an f before the quote, and any expression inside { } is evaluated and inserted (:.2f = exactly 2 decimal places). Phase 4 covers them fully.

Simple example

print("Hello")                       # Hello
print("Total:", 250, "INR")          # Total: 250 INR   (any types; spaces between)
print()                              # blank line
print("2026", "10", "15", sep="-")   # 2026-10-15
print("Loading", end="...")          # no newline at the end...
print("done")                        # Loading...done

Real-world example

A script printing a neat order summary, with errors sent to standard error so they can be kept separate from normal output:

import sys

name = "Asha"
items = 3
total = 1499.5

print(f"{name} bought {items} items for ₹{total:.2f}")   # Asha bought 3 items for ₹1499.50

if total > 1000:
    print("Warning: order needs manual review", file=sys.stderr)

print() is fine for scripts and learning; production backends use logging instead (Phase 33).

✅ Correct code

amount = 250
print("Total:", amount)          # separate arguments
print(f"Total: {amount}")        # f-string
print("Total: " + str(amount))   # explicit conversion

❌ Incorrect code and why it fails

print("Total: " + 250)

TypeError: can only concatenate str (not "int") to str

Why: + between a string and a number is ambiguous (add or join?), and Python refuses to guess.

result = print("Hi")
print(result)

Hi
None

Why: print() displays a value but returns None. Displaying and returning are different things, and mixing them up is a common bug once you write functions (Phase 9).

Exercises

E1. Predict the exact output.

print("a", "b", "c")
print("a", "b", "c", sep="")
print("x", end=" ")
print("y")
print(print("z"))

Answer:

a b c
abc
x y

The inner print("z") runs first and displays z. It returns None, which the outer print then displays.

E2. Print today's date as 15/10/2026 using three separate arguments "15", "10", "2026".

Answer: print("15", "10", "2026", sep="/").

Debugging problems

14. input()

First principles

Programs often need data from the person running them. input() reads a line of text from standard input (stdin), normally your keyboard.

Why it exists

It makes programs interactive: ask a question, get an answer, act on it, without changing the code for every new value.

How it works

  1. It shows the prompt text you pass in, without adding a space or newline.
  2. It blocks: the program stops and waits.
  3. It reads what the user typed, up to Enter.
  4. It removes the trailing newline.
  5. It always returns a str, even if the user typed 42.
Call Result
int("25") 25
int(" 42 ") 42 (surrounding whitespace is ignored)
int("12.5") ValueError
int("twenty") ValueError: invalid literal for int() with base 10: 'twenty'
float("12.5") 12.5
"10" + "5" "105" (string joining, not addition)

Never trust user input. Users make typos, leave fields empty, use the wrong format or send malicious input. Always validate and convert it. You'll handle errors with try/except in Phase 12, and validate API input with Pydantic in Phase 52.

Simple example

name = input("What is your name? ")    # end the prompt with a space
print(f"Hello, {name}!")

What is your name? Asha
Hello, Asha!

Real-world example

"""bill_split.py: Split a restaurant bill evenly."""

def main() -> None:
    total = float(input("Bill total (₹): "))
    people = int(input("Number of people: "))
    share = total / people
    print(f"Each person pays ₹{share:.2f}")

if __name__ == "__main__":
    main()

Bill total (₹): 2450
Number of people: 4
Each person pays ₹612.50

✅ Correct code

age = int(input("Age: "))               # "25" → 25
print(f"Next year you'll be {age + 1}")

price = float(input("Price: "))         # use float() for decimal numbers

❌ Incorrect code and why it fails

age = input("Age: ")       # the user types 25
print(age + 1)

TypeError: can only concatenate str (not "int") to str

Why: age is the string "25", not the number 25. Convert it with int().

age = int(input("Age: "))    # the user types "twenty"

ValueError: invalid literal for int() with base 10: 'twenty'

Why: int() can only convert text that looks like a whole number.

Answer:

"""receipt.py: Print a simple receipt."""

def main() -> None:
    item = input("Item name: ")
    price = float(input("Price (₹): "))
    quantity = int(input("Quantity: "))
    total = price * quantity

Debugging problems

D1. The user enters 10 and 5. The program prints 105 instead of 15. Why? Fix it.

a = input("First number: ")
b = input("Second number: ")
print("Sum:", a + b)

Answer: input() returns strings, and + on two strings joins them: "10" + "5" is "105". Convert first:

a = int(input("First number: "))
b = int(input("Second number: "))
print("Sum:", a + b)       # Sum: 15

D2. What goes wrong, and how do you fix it?

quantity = int(input("Quantity: "))     # the user types 2.5

Answer: int("2.5") raises ValueError: invalid literal for int() with base 10: '2.5', because int() only accepts whole-number text. If fractional quantities make sense, use float(). If not, keep int() and handle the error with try/except (Phase 12), telling the user to enter a whole number.

D3. The prompt and the user's typing run together, like Enter your name:Asha. What's the fix?

name = input("Enter your name:")

Answer: input() doesn't add a space after the prompt. End the prompt with one: input("Enter your name: ").
